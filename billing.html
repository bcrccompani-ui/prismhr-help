Chapter 2 Billing Codes There are billing codes that your organization must define and set up.

Rate Groups Use the Rate Groups form to maintain rate group codes. The system uses these codes to manage billing for benefit plans.

Note: Rate Group Codes can contain any alphanumeric characters except 0. They also cannot contain a period (.).

To set up a rate group: 1. Enter the Rate Group code. 2. Enter a description of the rate group in the Group Name field. 3. Select Inactive if this rate group is not currently used in PrismHR. 4. Select Premium Rate Group to use this rate group for premiums instead of billing. 5. Click Save. When you select an existing Rate Group and save the form, the system checks for the following validations for the Premium Rate Group checkbox: • If the Premium Rate Group field is checked, then on clicking Save, the system verifies that there are no Billing Rate records associated with the selected Rate Group. • If the Premium Rate Group field in unchecked, then on clicking Save, the system verifies that there are no Premium Rate records associated with the selected Rate Group.

Note: If any Billing Rate or Premium Rate is found in any of the above mentioned validation, an error message stating, Rates are currently associated with this Rate Group. Changes to the ‘Premium Rate Group’ are not allowed. is displayed.

Using Billing Codes Use the Billing Codes form to define billing entry and accounting information. There are certain bill codes that PrismHR requires, and rules for others. Here is a list of codes used as system defaults and their usage: • 000: Gross Wages • 001: FICA/OASDI • 002: FICA/Medicare • 003: FUTA • 004: SUTA • 004O: Other State Tax (when needed) • 005: Workers’ Compensation • 005D: Workers’ Compensation Discount • 006: Administrative Fee • 006D: Administrative Fee Special Discount • 006M: Adminstrative Fee Adjust to Min/Max All other codes are added to the end of the list at bill time, such as benefits and deductions. Sales tax codes are formatted TAX{xx}, where xx is the two-character state code, for example, TAXOH for Ohio state tax. TB{BenefitPlanID} is the first bill code checked during the termination of an employee’s benefits. For example, a benefit plan MEDABC would look for the bill code TBMEDABC. If present, the system uses that, otherwise the system looks for a code TEBA (terminated employee benefit acceleration). This method gives the ability to create accounting detail where it is warranted while lumping smaller plans into one TEBA bucket.

Establishing Billing Events You can use the Billing Events form to establish events to bill, or override prices for various items. There are certain events that PrismHR requires, and rules for others. Here is a list of codes used as system defaults and their usage: • 000: Payroll Generated; you cannot edit the bill code for this event. Those codes are predefined. • NESxx: New Employee Setup, where xx is the employment type. If the system does not find an NES code with the appropriate employment type, it uses the standard NES code. • TEPxx: Terminated Employee Processing, where xx is the employment type. If the system does not find a TEP code with the appropriate employment type, it uses the standard TEP code. • RHSFEE: Rehire Setup Fee. Auto-bills for employees of any type when there is no specific FT/PT designation. • RHSFEEF: Rehire Setup Fee Full Time Employees. Auto-bills for employees of any type when there is no specific FT/PT designation.

Avoiding Pitfalls Client Bill Pending is an extremely useful tool; at the same time, problems can occur if you are not careful. PrismHR does only what you tell it to do, so ensure your entries are correct. Client Bill Pending is both employee- sensitive and date-sensitive.

Employee Sensitivity For example, you set up a new employee named Joe, who is an active employee and is paid once a month on the first. You create a line item for Joe on the second day of the month. PrismHR does not convert the line item into a bill for the client until Joe’s next pay day, which is the first of the following month. If this feature was not employee-sensitive, you would bill the client on the next invoice, which could fall before the first of the month.

Date Sensitivity For example, you create a line item for January 1, 2024, but specify a billing date of January 1, 2026 by mistake. The line item remains dormant in PrismHR until the date you specified, then is included in the next invoice after that date.

Using Repeat Thru Date Correctly If you set up a recurring event, you must define the date limits of the event. The system uses the Repeat Thru Date field to know when the recurring event starts and when it stops. Be very aware of the dates you want to define and double-check your date entries. The system automatically calculates if any dates have been “missed” upon the first payroll run after you define the recurring event.

For example, you have a weekly billing event for a payroll that you want to occur starting on or after January 1, 2024. You enter 12/31/24 in the Repeat Thru Date field. However, you mistakenly enter the start date (in the Bill Date field) as 1/1/23 instead of 1/1/24. Upon January 2, 2024 (the first business day of the year), PrismHR realizes it has not performed its weekly billing (based on the check date) since the starting date. Therefore, PrismHR creates 52 transactions in order to “catch up” to the present date.

Using Repeat Cycle Correctly If you set up a recurring event, you must define how often to repeat the event. The system uses the Repeat Cycle field to know how often it must run the recurring event. For example, you have a monthly billing event for an end-of-the-month payroll. The system reads what you enter literally: in other words, it is very exact. You mistakenly enter the billing date (in the Bill Date field) as 1/31/24 instead of 1/28/24. Upon February 29, 2024 (because of the leap year – otherwise February 28), PrismHR realizes it is not the 31st day of the month. Therefore, PrismHR skips the transaction.

Cost If you enter an amount in the cost section of Bill Pending, the cost is updated when a payroll is posted. For example, you need to set up a client bill pending for an overbilling on SUTA. The rate you charge your client is 2.7% and you mistakenly charged them 3.00% on $15,000 taxable wages. SUTA is not a profit center for this client so the billing should match the cost. The liability was calculated at the correct rate of 2.7%. When entering the client’s credit for $45.00, leave the cost column blank. There is no need to adjust cost.
